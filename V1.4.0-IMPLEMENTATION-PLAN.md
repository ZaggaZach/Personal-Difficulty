## 2. Proposed architecture

**A. Permission and selection model [Proposal]**
- **Pure decision function:** `SelectionPolicy.decide(actor, targetPlayer, requestedMode, state)` returns `Allowed`, `Denied(reason)` or `NoChange`. It is the single source of truth, used by commands, the GUI and tests.
- **Per-player record, v2:**
  - `mode`
  - `lock` (a boolean, plus who set it and when)
  - `allowed`: an optional allow-list, where null means "follow the server policy"
  - `assignedByAdmin` (informational)
  - On disk: `{"version":2,"players":{"<uuid>":{"mode":"ELITE","locked":true,"allowed":["NORMAL","ELITE"],"by":"<adminUuid>","at":...}}}`
- **Rules:**
  1. A player may select mode M only if they are not locked, M is globally enabled, and M is in their allow-list (when they have one).
  2. An administrator may assign any mode to anyone, ignoring both the global policy and the allow-list. The assignment can optionally lock the player.
  3. A locked player cannot change their own mode. They keep it until an administrator unlocks them. Locks survive a globally disabled mode.
  4. An allow-list can never be empty, and an admin edit that would make it empty is refused. If the current mode is not on the new allow-list the admin must pick one of three choices: switch the player, keep the mode as an exception, or abort.
  5. "Lock to a mode" and "restrict choices" are separate switches, so both can exist at once.
- **Migration:** v1 files load unchanged (every entry becomes `mode` only). The file is rewritten as v2 only when something changes, with a timestamped backup of the old file first. Unknown entries are preserved, as today.

**B. Setting registry [Proposal]**
- A table of `SettingDef` records: key, type, min, max, default, step, apply mode (`LIVE`, `NEXT_SCAN`, `RESTART`), display name, description. Every setting in `PdConfig` becomes one.
- The loader, the GUI, the validator and `admin config` all read this table, so a setting cannot exist in one but not another.

**C. GUI [Proposal]**
- **Engine:** the Gift Mailbox pattern: chest menus, locked slots, and a click router that accepts only plain presses.
- **Entry:** `/personaldifficulty admin gui` (or `/pd gui`). It is permission-checked at open and again on every click via `stillValid` and an explicit check in `onPress`.
- **Pages:**
  1. Difficulty Settings: one page per mode, with `−`/`+` buttons (shift-click for a bigger step) and a reset-to-default button per setting and per page.
  2. Player Management: a paged list of online players plus known offline ones from the user cache; actions are assign, lock or unlock, reset, and a per-player status card.
  3. Difficulty Permissions: the server-wide enable/disable toggles and a per-player allow-list editor.
  4. Advanced Settings: the Elite overhaul settings and effect chances, with Apply-timing labels.
- **Numeric input:** `−`/`+` buttons only in v1 of the GUI. Exact values need an anvil text prompt (feasible but extra work) or the command line (Q5).
- **Security:** never trust slot contents. The server holds the page state, and the client only sends slot indices.

**D. Elite hunting network [Proposal]**
- Per-level `AlertBoard`: a small bounded map of `targetUuid → (lastKnownPos, lastSeenTick, hopCount)`.
- Mobs publish a sighting when they see an Elite player. Others read the board during their existing scan tick.
- A mob that receives an alert goes to the last known position (see C below) and does not get exact tracking.
- Bounds: a maximum number of entries per level, a maximum hops, a radius, a time-to-live, and per-tick work caps. Details in section 3.

## 3. Feasibility, feature by feature

### A. Admin GUI
- **Feasible. [Fact]** Gift Mailbox demonstrates the pattern with a vanilla client, including a lot of hostile-click handling.
- **Permissions [Fact]:** `fabric-permission-api-v1 1.0.8` is present in the Fabric API 0.165.0 distribution listed in the 1.3.0 test logs, so permission nodes are possible. The default can fall back to op level 2.
- **Limits [Fact]:** a chest menu is at most 6×9 slots, so large lists need paging, and numeric input is button-based.
- **Vanilla permission API call for "is op level 2" on a `ServerPlayer`:** not yet checked. The command path uses `Commands.hasPermission(LEVEL_GAMEMASTERS)`. The GUI re-check will use the same permission set, to be confirmed in phase 0.

### B. Permission rules
- **Feasible; no API risk.** It is pure logic plus persistence. All the complexity is in testing the combinations (section 5).

### C. Elite overhaul

| Item | Verdict | Verified facts and notes |
|---|---|---|
| Detection at least 3× | **Partly feasible.** | Acquisition is a distance check plus line of sight, which is cheap at any radius. Today's clamps are 2.0 and 64 blocks. A zombie's vanilla range is about 35, so 3× is about 105. Mobs far from players may not be entity-ticking at all (a server setting), so the effective ceiling is the server's simulation distance. **Proposal:** raise the multiplier clamp to 3.0 and keep an absolute cap, with a decision on its value (Q6). |
| Pursuit path to that range | **Not as one A\* search.** | **[Fact]** `createPath(BlockPos, reach, maxPathLength)` exists, but node budget is about `followRange × 16`. A 100+ block route will come back partial. **Alternative:** walk in waypoint hops along the heading, re-planning every few seconds (this also gives "searching" behaviour). |
| Memory up to 5× | **Feasible.** | **[Fact]** vanilla unseen memory is 60 ticks (`TargetGoal.unseenMemoryTicks`). 5× is 300 ticks. The 1.2.0 hook already scales it; the clamp (4.0) and the 400-tick cap need raising. |
| Alert network (64 blocks, 60 s) | **Feasible as designed above.** | **[Fact]** vanilla `HurtByTargetGoal.alertOthers` already alerts same-type mobs inside the follow range (one hop, same class). The board generalises it. Limits: a hop budget (suggest 2–3), a per-level entry cap, one scan per mob per interval, TTL 1,200 ticks, and no chains between dimensions. |
| Search last known position | **Feasible.** | A custom goal added in `Mob.registerGoals` (**[Fact]** it is a protected method, so a mixin `@Inject` at its tail works). It uses `PathNavigation.moveTo`. It must not read the live player position: it stores the position at the moment of last sight. |
| No omniscience | **Design constraint.** | Only positions captured with line of sight enter the board. Alerts carry a position and a time, never the player entity, and the position goes stale as the player moves. |

**Status effects.** Extending `PdMobEffects` is straightforward (**[Fact]** the code is structured per family). Candidate additions are a table of (mob, effect, chance, duration) in the setting registry. Keep the vanilla-duplicate rules (husk, stray, bogged, cave-spider poison).

### D. Skeleton threat
- **[Fact]** `AbstractSkeleton.performRangedAttack` aims at the target's **current** position with a fixed speed of 1.6, plus an arc fudge `distance × 0.2`, and uses the entity's `rangedAttackUncertainty`.
- **[Fact]** Arrow gravity is 0.05 per tick and inertia 0.99 (`AbstractArrow`). The damage is `ceil(speed × baseDamage)` with a base of 2.0, so a speed of 2.4 instead of 1.6 raises arrow damage by roughly 50%. On top of Elite's ×2 that matters for balance (Q7).
- **[Fact]** A `ServerPlayer`'s velocity on the server comes from `getKnownMovement()`, which returns the last movement the client reported, so it is usable for prediction. Real clients report it; mock players do not.
- **Algorithm [Proposal]:** iterate a few steps: guess flight time t, predict target position = pos + velocity × t (with the player's jump/fall handled by gravity if airborne), solve the launch pitch for gravity and drag, update t, and repeat 3–5 times. Blend with the vanilla aim by a configurable strength.
- **Interval:** the vanilla interval is 40 ticks on Easy and Normal and 20 on Hard (**[Fact]**, `getHardAttackInterval`). "About half of vanilla" is ambiguous. 1.2.0 already gives Elite the Hard value (20). Q8 asks which baseline you mean.
- **Not claimable:** perfect accuracy. A player who changes direction after the arrow leaves will still dodge. Settings: strength, velocity multiplier, interval multiplier, maximum range.

### E. Enderman Blindside
- **[Fact]** `Enderman.teleport()` (random, called when stared at or hurt) and the private `teleportTowards(Entity)` (called when the target is farther than 16 blocks), both ending in the public `teleport(x, y, z)`. That final method uses `randomTeleport`, which already checks collision and valid ground, so a mixin that only changes the **coordinates** inherits vanilla's safety.
- **Plan [Proposal]:** wrap the two callers. If the mob's target is an Elite player and the mob is already hostile (target non-null), compute a candidate behind the player (opposite their look direction at a configurable distance, with a configurable random offset), probe a few candidates, and call vanilla `teleport(x,y,z)` with the first that passes our own footing and collision check. If none passes, call the original method unchanged.
- **Constraints preserved:** anger triggers are untouched, as is idle teleporting, and Endermen are never made hostile.

### F. Configuration and migration
- Feasible with the registry. Proposed apply timing: most numeric settings are read at the next scan or hit, so `LIVE`. Registered goals and mixin-time behaviours (if any are added) are `RESTART`.

## 5. Test matrix and acceptance criteria

Each layer proves something different. No layer's results substitute for another's.

| Layer | What it can prove | What it cannot prove |
|---|---|---|
| Unit tests | Pure rules, parsing, migration, clamping | Anything involving a live server or mob |
| GameTests (mock players) | Mob AI, damage, effects, persistence in a world | Real network behaviour, real client input |
| Headless protocol bot (Gift Mailbox style, real server process) | GUI over the real protocol: opening, click handling, malformed and hostile packets, permission denial | How it looks or feels in a graphical client |
| Graphical-client playtest (you) | Rendering, text, feel, difficulty balance, multiplayer lag | Anything that is not played |

**Matrix**
- **Regression:** the whole 1.3.0 suite (94 unit, 116 GameTests) green on the 1.4.0 branch before and after each phase.
- **Modes:** every mode × every mechanic (damage, hunger, healing, effects, targeting), reusing the existing suites.
- **Permissions:** a generated table covering actor (self, admin, console, non-op) × global enabled × allow-list (none, includes mode, excludes mode) × lock (on or off) × requested mode (all five): roughly 200 cases, with expected outcomes from the rules above.
- **Persistence:** death, respawn, disconnect, restart and `kill -9` for mode, lock and allow-list; v1-to-v2 migration with unknown entries, truncation and backup.
- **GUI access:** open as a non-op (denied), as an op, after demotion mid-session, stale container ids, malformed click packets, shift-click and drag, hostile floods, and a server-health check at the end (same as Gift Mailbox).
- **Config:** each setting's min, max, NaN, default, reset and reload; a failed write leaves the previous config intact.
- **Elite:** per behaviour, a live-AI GameTest plus a mutation check (as in 1.3.0); the alert board's bounds (hop limit, entry cap, TTL expiry, radius edge).
- **Skeleton:** statistical hit rate against a moving mock player at fixed speeds, against vanilla aim, plus non-Elite regression.
- **Enderman:** only valid destinations (open space, solid footing, no fluid), a fallback when none exists, no anger changes, no Endermen made hostile.
- **Performance:** a measured tick-time ceiling with a large mob crowd, alert propagation under a burst, and a soak run.
- **Client compatibility:** the protocol bot proves the packets are accepted by the server's side of a vanilla protocol. A graphical vanilla client run is the only evidence for client-side rendering.
- **Dedicated-server playtest:** yours; I cannot perform it.

**Acceptance per phase (objective)**
- **P1:** 100% of the generated permission matrix passes; v1 files load byte-identically unless a change is made; the old suite is unchanged.
- **P2:** every setting has a registry entry; a round trip of write, reload and read yields the same value; a corrupted file is rejected with the old config kept.
- **P3–4:** the protocol-bot suite passes, including zero uncaught exceptions or ERROR lines; a non-op can never change state through any screen; every GUI action matches its command equivalent.
- **P5:** each bound (ranges, memory, hops, TTL, entry cap) enforced by a test; no mob acquires an Elite player through a wall; a measured tick cost below the agreed budget.
- **P6–7:** per mob, a live-AI test and a mutation failure; each mob's non-Elite behaviour unchanged.
- **P9:** clean build, all layers green three times in a row, docs list what was and was not tested.

## 6. Risks
- **Performance:** a 3× range and a shared board raise per-tick work. Mitigations are caps, throttles and measuring early (phase 5).
- **Balance and fairness:** 3× detection, 5× memory, predictive 1.5× arrows and an alert network may make Elite effectively unwinnable for most players. Ship every number as a setting and test with real players.
- **Mixin fragility:** Enderman and skeleton hooks touch private methods that can change between Minecraft versions. Keep fallbacks to the vanilla call.
- **Brain-driven mobs** (piglins, hoglins, the Warden) do not use the goal system, so the shared hunting code does not apply to them.
- **Migration:** a mishandled v2 file would lose player assignments. Backups plus a read-only first pass mitigate this.
- **GUI:** it is only as safe as its click router, so hostile-click tests are mandatory.
- **Mob chunk activity:** mobs outside simulation range will not react at all, regardless of settings.

## 7. Decisions I need from you
1. **Inherit.** It does not exist in 1.3.0. Do you want it re-introduced (and what would it mean now that Normal is the default), or should 1.4.0 stay with five modes?
2. **Lock semantics.** Should a locked player be unable to change mode at all (my proposal), or only unable to leave their locked mode while other restrictions still apply?
3. **Permission model.** Is op level 2 for the GUI enough, or do you also want Fabric permission nodes (`personaldifficulty.admin.gui`, `.assign`, `.lock`) with op level 2 as the fallback?
4. **How GUI edits reach the config file.** (a) Patch the existing `.properties` line by line, keeping comments and backing up first; or (b) store GUI changes in a separate overrides file layered on top. I recommend (a).
5. **Numeric input.** Is `−`/`+` buttons enough, or do you want an anvil text prompt for exact values?
6. **Range cap.** A true 3× on a 35-block mob is about 105 blocks. Keep an absolute cap (and at what number), or let the multiplier alone decide?
7. **Arrow speed 1.5×** also raises arrow damage by about 50% before Elite's ×2. Should I compensate by lowering base damage, or is the extra damage intended?
8. **"Half the vanilla interval."** Half of vanilla Normal (20 ticks, which 1.2.0 already gives) or half of Hard (10 ticks)?
9. **Scope of Warden and Nether mobs.** Include the Warden anger boost at all? Defer piglins and hoglins?
10. **Release shape.** Ship the GUI, permissions and Elite overhaul together as 1.4.0, or split the GUI/permissions into 1.4.0 and the Elite overhaul into a later release?

I will not start phase 0 until you approve the plan and answer the questions that matter to you.
