**Contradictions found and resolved**
1. *Revision 1 said the GUI would edit the `.properties` file and `admin config` would read it.* Now: the GUI only writes the overrides file; `.properties` is read-only to the mod; `admin config` shows the effective value and its source (default, properties, override).

3. *Revision 1 asked whether "half the interval" meant 20 or 10.* Resolved to 10, but the plan now states that this is the countdown after a shot, not the whole shot cycle (section 6.4).

## 3. Permission and selection model

**Per-player record, v2** [Proposal]: `mode`, `locked` (with who set it and when), `allowed` (optional allow-list; null means "follow the server policy"), `by` (last admin who changed it). On disk: `{"version":2,"players":{"<uuid>":{"mode":"ELITE","locked":true,"allowed":["NORMAL","ELITE"],"by":"<uuid>","at":<millis>}}}`.

**Rules (the complete, final set)**
- **R1.** A self-service change to mode M is allowed only if: the player is not locked, M is globally enabled, and M is in the player's allow-list (when set). Otherwise it is refused with a specific reason and nothing changes.
- **R2.** An administrator may `assign` any mode to any player (including themselves) regardless of global policy, allow-list or lock, optionally locking at the same time. An assignment may produce a mode the player could not choose themselves.
- **R3.** A locked player cannot change their own difficulty by any path. Only an administrator can unlock them.
- **R4.** A lock survives death, respawn, disconnect, restart and later changes to the global policy (disabling a mode never changes anyone's saved mode, as in 1.1.0).
- **R5.** An allow-list may never be empty. An admin edit that would remove the player's current mode from the list must choose one of: switch the player to a listed mode, keep the current mode as a recorded exception, or cancel.
- **R6.** `restrict` and `lock` are independent. A locked player with an allow-list stays locked; the allow-list applies if they are later unlocked.
- **R7.** `admin reset <player>` sets Normal, clears the lock and clears the allow-list. `unlock` and `unrestrict` do the narrower operations.
- **R8.** An operator using the ordinary self-service command is an ordinary player (R1 applies). Only `assign` overrides.

**Migration:** v1 loads unchanged (entry becomes `mode` only). The file is rewritten as v2 only when something changes, after a timestamped backup of the previous file; unknown entries are preserved verbatim, as today. A v2 file read by 1.3.0 is not supported (documented downgrade note: restore the backup).

## 4. Configuration: overrides file, migration and apply timing

- **Layers (lowest to highest):** built-in defaults, then `config/personaldifficulty.properties` (hand-edited, never written by the mod), then `config/personaldifficulty-overrides.json` (written only by the GUI and `admin set/unset`).
- **Overrides format [Proposal]:** `{"version":1,"values":{"elite.damage-multiplier":2.5,...}}`. Only keys that differ from the lower layers are stored. `unset` (and the GUI "reset to default") removes the key. "Reset page" removes all keys of that page.
- **Validation:** every key must exist in the `SettingRegistry`; each value is range-checked and type-checked before any write. An invalid `set` is refused with the allowed range. An invalid value found in the file on load is ignored with a warning (the lower layer's value is used) and the file is not rewritten.
- **Safe writes:** write to a temp file, fsync, atomic rename; keep the previous file as `personaldifficulty-overrides.json.backup-<time>` (bounded to the last 5). A failed write leaves the active configuration unchanged and reports the error.
- **Migration:** none needed for existing servers (no overrides file means identical behaviour). The existing `.properties` file and its defaults template are untouched, except that the template gains documentation for new keys when it is first created on a fresh server (existing files are never edited).
- **Introspection:** `admin config` lists effective values with their source (default, properties, override). `admin get <key>`, `admin set <key> <value>`, `admin unset <key>` provide exact values (permission level 2, console allowed).
- **Apply timing** [Proposal], shown in the GUI and `admin get`: `LIVE` (next hit or next scan; all multipliers, chances, durations), `NEXT_SCAN` (hunting parameters, picked up within one scan interval), `RESTART` (anything requiring goal registration; the plan tries to have none).
- **Reload:** `admin reload` re-reads properties, overrides and the availability file; a failure in one keeps that layer's previous values.

## 6. Elite overhaul

### 6.1 Ranges and memory (decision 6)
- Detection (acquisition): effective range = min(vanilla range x `acquisition-range-multiplier`, `absolute-range-cap`), never below the vanilla range. The multiplier clamp rises from 2.0 to 3.0; the absolute cap setting defaults to 128 (valid 16-256); the 1.3.0 hard-coded 64 is removed.
- Cost: acquisition is a distance test plus one line-of-sight ray per candidate per scan, so it scales cheaply. **[Fact]** Mobs only act when their chunk is entity-ticking, so the real ceiling is the server's simulation distance (a server with 8 chunks cannot have mobs react beyond about 128 blocks regardless of this setting). This is documented and shown in `admin config`.
- Pursuit memory: unseen-memory multiplier clamp rises from 4.0 to 5.0 (60 ticks x 5 = 300 ticks); the 400-tick ceiling in `EliteSurvival` stays above it. This is separate from the alert memory below.

### 6.2 Pursuit beyond the path-search budget
- **[Fact]** `PathNavigation.createPath(BlockPos, reachRange, maxPathLength)` exists, but the node budget is about follow range x 16, so 100+ block routes come back partial.
- Proposal: pursue in waypoint hops (a new bounded goal): every few seconds choose a reachable intermediate point toward the last known position and walk it with ordinary pathfinding; never straight-line movement, never through blocks.

### 6.3 Last-known position and alert network
- `AlertBoard` per level: bounded map of `targetUuid -> (lastKnownPos, tick, hops)`. Entries are written only when a mob **has line of sight** to the Elite player, and carry a position and time, never the player entity. Positions go stale as the player moves.
- Mobs that lose sight search the last known position (`LastKnownGoal`, added from a tail `@Inject` in `Mob.registerGoals`; **[Fact]** it is a protected method called from the constructor), then give up. This is explicitly separate from "current target tracking".
- Propagation: a mob that learns of a sighting may relay it to eligible hostile mobs within the alert radius (default 64) with a hop budget (default 2), a per-mob relay cooldown, and a per-level entry cap. Alert memory (default 60 s = 1,200 ticks) is a TTL on board entries. Relaying runs only on a mob's own scan tick with a per-tick work cap. No cross-dimension alerts. No exact positions after sight is lost.
- **[Fact]** vanilla's `HurtByTargetGoal.alertOthers` already does a single-hop same-class alert; the board generalises it.

### 6.4 Skeleton threat (decisions 7 and 8)
- **[Fact]** `AbstractSkeleton.performRangedAttack` aims at the target's current position with fixed speed 1.6 and an arc fudge `distance x 0.2`; arrow gravity is 0.05 and inertia 0.99; arrow damage is `ceil(speed x baseDamage)` with `baseDamage` 2.0 (`AbstractArrow`).
- **[Fact]** `ServerPlayer.getKnownMovement()` returns the last movement reported by the client, usable for prediction (mock players report none).
- **Independent controls [Proposal]:** `elite.skeleton.arrow-speed-multiplier` (default 1.5), `elite.skeleton.arrow-damage-multiplier` (a separate scale on the arrow's base damage, default 1.0), `elite.skeleton.prediction-strength` (0-1), `elite.skeleton.max-range`, `elite.skeleton.firing-interval-ticks` (default 10).
- **Speed and damage are separate controls, with no compensation formula.** The mod does **not** divide damage by the speed multiplier and does not claim that doing so would cancel the effect of faster arrows. [Fact] vanilla damage is `ceil(speed at impact x baseDamage)`, so a faster arrow can deal more damage by vanilla physics alone. The speed setting changes launch speed; the damage setting scales base damage; nothing links them. What actually happens is **measured in 26.3 and documented**, not assumed.
- **Unavoidable vanilla physics effects to document, not to engineer away [Fact unless marked]:** (1) damage uses the speed at impact, and the arrow decelerates (inertia 0.99 per tick) and drops (gravity 0.05), so the damage at a given distance depends on launch speed and flight time together; (2) `ceil` makes the damage change in whole steps, so small speed changes may do nothing and others add a full point; (3) a full-power draw can make the arrow critical, which adds a random bonus to damage; (4) enchantments or an effect on the bow carrier, Piercing/Punch-type behaviour and a target's armour and Resistance act after this calculation; (5) [Assumption to be measured] hit-rate and the share of the arrow's flight spent in water or against walls change the damage actually dealt.
- **Measurement (acceptance, section 9):** record the actual damage dealt to a stationary mock player at fixed distances for vanilla settings and for each tested speed and damage multiplier, with sample sizes, and report the mean, spread and any distance where faster arrows raise damage. Any decision to compensate (for example by lowering `arrow-damage-multiplier`) is made by you from those numbers; any intended damage increase is deliberate and documented.
- **Firing interval: starting target, then measure [Fact + Proposal]:** `firing-interval-ticks` is the countdown after a shot in `RangedBowAttackGoal`, and a shot additionally needs a fixed 20-tick draw (`pullTime >= 20`). The starting target is the 10-tick countdown. Because the arithmetic suggests a cycle of about 30 ticks (versus about 60 on Normal and 40 on Hard, and 1.2.0's 40), that figure is a **hypothesis to be measured**, not a promise: the real cycle (shots per fixed time, with and without line of sight interruptions, strafing and target loss) is measured in 26.3 and recorded in the verification report.
- **Draw time is not changed automatically.** The 20-tick draw stays as vanilla. Any shortening requires a separate setting `elite.skeleton.draw-ticks` (default 20, equal to vanilla) and your explicit approval before it is implemented.
- **Prediction algorithm [Proposal]:** iterate 3-5 times: estimate flight time, predict target position from reported velocity (gravity if airborne), solve launch pitch with gravity 0.05 and drag 0.99, re-estimate time. Blend with vanilla aim by `prediction-strength`. Never promised: perfect accuracy; a player who changes direction after release still dodges.

### 6.5 Enderman Blindside
- **[Fact]** `Enderman.teleport()` (random; on being stared at or hurt), the private `teleportTowards(Entity)` (when the target is over 16 blocks away), both ending in the public `teleport(x,y,z)`, which uses `randomTeleport` and therefore keeps vanilla's collision and ground validation.
- Proposal: wrap the two callers; only when the Enderman is **already hostile** (target is an Elite player) choose candidate positions behind the player (opposite their look direction, configurable distance and random offset), pre-validate collision space and solid footing ourselves, and pass the first valid candidate to vanilla `teleport(x,y,z)`. If none is valid, call the original behaviour unchanged. Anger triggers and idle teleporting are untouched, and no Enderman is made hostile.

### 6.7 Effects expansion
A per-family table in the `SettingRegistry` (mob, effect, amplifier, chance, duration), keeping the 1.3.0 rules: real damage only, no doubling of vanilla effects (husk Hunger, stray/bogged arrows, cave-spider poison), bounded durations. Additions are decided at the start of phase 8.

### 6.8 Warden and Nether (decision 9)

Rule: the only mechanism allowed is raising anger through the vanilla anger API for an Elite player the Warden could legitimately sense (inside its vibration/smell mechanics). No direct target forcing, no extended range, no wall-sensing.

## 8. Gates, deferral protocol and release rule

- **Go/no-go gate** for each risky feature (Warden, piglin/hoglin, door-breaking, creeper fuse, drowned, Blindside, prediction): (1) a written feasibility note with verified APIs; (2) a live-AI GameTest passing three times in a row; (3) a mutation check that fails when the hook is disabled; (4) non-Elite behaviour unchanged in a regression test; (5) the performance budget below. Failing any item means the feature is deferred.
- **Deferral protocol:** if a gate fails, I stop work on that feature and report it to you with the evidence and the alternatives **before** any scope change. Nothing is dropped, weakened or shipped half-working silently.
- **Release rule:** 1.4.0 ships only when every shipped feature has passed its gate; risky features that pass but have not been played by you ship **disabled by default** with a documented switch. Features that fail are listed as deferred in the changelog.
- **Performance: a measured target, not a guaranteed outcome.** The proposed target is a mean tick-time increase of no more than 1 ms with 200 hostile mobs and 5 Elite players, compared with the same scenario with no Elite player online. It is not assumed to be achievable. The performance report must record: the baseline (mean and spread of tick time, with the test server's hardware, Java settings, world, view and simulation distance, mob types and counts, player setup, warm-up and sampling method); the same measurements with each feature switched on separately and together; the results; and every regression or miss against the target, stated plainly. Alert-board work per tick stays bounded by constants asserted in tests. If the measurement exceeds the target, the 128-block cap and other limits are reduced or the feature is deferred under the section 8 protocol, and you decide.

## 10. Risks
- **Performance:** larger ranges, the alert board and waypoint pursuit add per-tick work; mitigated by caps, scan throttling and an early measurement (P5).
- **Balance and fairness:** 3x detection, 5x memory, predictive 1.5x-speed arrows at roughly double the vanilla rate, alert chains, Warden anger: Elite may become effectively unwinnable. Every number is a setting and risky pieces ship disabled by default until you have played them.
- **Simulation distance:** mobs outside entity-ticking chunks do nothing, so a 128-block cap cannot exceed the server's own simulation distance.
- **Mixin fragility:** private-method hooks (Enderman, skeleton) may break on a Minecraft update; every hook falls back to the vanilla call.
- **Brain-driven mobs** (Warden, piglins, hoglins) need different mechanisms and may be deferred.
- **Migration:** a mishandled v2 file could lose assignments; mitigated by backup-before-write and unknown-entry preservation. **Downgrade:** 1.3.0 cannot read v2 (restore the backup).
- **Overrides vs hand edits:** a key in both layers means the override wins; the GUI and `admin config` show the source so this is visible, and removing the override restores the properties value.
- **GUI:** only as safe as its click router and per-action re-validation.
